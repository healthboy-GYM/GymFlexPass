## 3. 만든 계기 · 해결한 문제

**계기 — 대형 프랜차이즈인데 얼굴이 없었다.**
헬스보이짐은 전국 규모의 대형 헬스장 프랜차이즈지만 **제대로 된 공식 웹사이트가 없어 온라인 브랜딩·마케팅 자체가 불가능**한 상태였다. 그래서 (1) 헬스보이짐 **브랜드를 소개**하고, (2) 브랜드를 대표하는 통합 이용권 **'헬보올패스'를 홍보**하는 페이지를 직접 만들었다. 그 결과 이 사이트는 현재 **네이버·구글 검색에서 상단에 노출**되며 브랜드의 온라인 유입 창구 역할을 하고 있다.

이 큰 목표 아래 두 개의 실무 문제를 풀었다:

- **분산된 지점 정보 → 한 곳에서 탐색·비교**: 지점마다 등급·종목·주차·부대시설이 제각각이라, 방문자가 "내가 다닐 동선에 어떤 등급이 필요한지" 판단하기 어려웠음. 지도와 등급 추천으로 이 판단을 자동화.
- **운영 자립(비개발자 인수인계)**: 회사에 개발자가 없음. 가격 변경·이벤트 팝업·공지 하나 바꾸는 데도 개발자가 필요하면 운영이 멈춤. → **코드를 몰라도 관리자 화면에서 사이트 전체를 바꿀 수 있는 CMS**를 설계 목표로 삼아 대부분 달성.

## 5. 아키텍처 개요

```
방문자 ─┐
        ├─▶ Next.js (App Router, SSR)  ──▶ Firestore (공개 읽기)
관리자 ─┘         │                              ▲
                  │ Server Actions               │ 관리자 쓰기(인증)
                  ├─▶ 지오코딩(Naver, 서버 시크릿) │
                  └─▶ 등급 추천 알고리즘            │
                                                  │
        관리자 CMS(/admin) ───── 실시간 구독/저장 ──┘
                  │
                  └─▶ Firebase Storage (사진/영상 업로드)
```

**핵심 설계 원칙 — "콘텐츠는 코드에서 분리한다"**
- 사이트의 거의 모든 콘텐츠(가격·팝업·배너·FAQ·이용안내·지점)는 Firestore `settings/*`·`gyms` 문서에서 파생.
- 각 데이터 계층(`src/lib/*.ts`)은 **문서가 없으면 하드코딩 기본값으로 폴백** → 저장 전에도 사이트가 안전하게 동작.
- 관리자가 값을 바꾸면 **Firestore 실시간 구독으로 방문자 화면에 즉시 반영**(콘텐츠 변경에 재배포 불필요).

## 6. 핵심 기능

### 6-1. 지점 탐색 & 등급 자동 추천 (`RouteFinderSection`, `actions.ts`)
- 네이버 지도 위에 71개 지점을 등급별로 표시하는 **BranchLocator**.
- 사용자가 다닐 지점들을 선택하면, **서버 액션이 최적 등급을 추천**:
  - 등급 기본 점수 + 편의시설 선호도(주차·사우나·안마의자·웨이트 브랜드) 가점
  - 선택 지점들의 중심 좌표 대비 **하버사인 거리로 근접성 반영**
  - "한 등급 낮추면 이용 못 하게 되는 지점"까지 계산해 **업그레이드/다운그레이드 트레이드오프를 설명**
- 결과에 월 요금·지역별 안내 메시지를 함께 노출해 구매 전환으로 연결.

### 6-2. 자립형 관리자 CMS (`/admin` + `*Manager.tsx`)
개발자 없이 운영진이 사이트 전체를 관리:
| 관리 탭 | 하는 일 |
|---|---|
| **지점 관리** | 지점 CRUD, 대표 사진·드론 영상 Storage 업로드, **주소 입력 시 좌표 자동 지오코딩** |
| **가격 관리** | 상품 추가/삭제/순서변경, 등급×기간별 가격·결제 링크 편집 → 구매 페이지·업그레이드 차액표 자동 파생 |
| **팝업 관리** | 단일 목록 모델로 모든 팝업 on/off·순서·수정·삭제 (바디챌린지·당첨자 등 기본 팝업도 편집 가능, 마감일 자동 만료) |
| **배너·공지** | 상단 배너 문구·색상·링크·표시 여부 (현재 표시 중인 배너를 그대로 불러와 수정) |
| **이용안내 · FAQ** | 단계/카테고리/Q&A CRUD, 가벼운 마크다운 렌더 |
| **이벤트 관리** | 프로모션 페이지 콘텐츠 |
| **사용법(매뉴얼)** | 각 탭 사용법을 담은 **비개발자 인수인계용 가이드** |

### 6-3. 마케팅 랜딩 (`page.tsx` 및 `sections/*`)
- Hero, 통계 카운트업(`CountUp`), 스크롤 등장 애니메이션(`Reveal`), 전국 지점 사진 마퀴(클릭 시 드론 영상 모달), 이벤트 쇼케이스 등 **전환 중심 랜딩 페이지**.

## 7. SEO · 브랜딩 · 마케팅 (핵심 성과)

"공식 웹사이트가 없어 마케팅이 불가능했다"는 최초 문제를 정면으로 해결한 영역. **네이버·구글 검색 상단 노출**이라는 성과의 기반을 직접 구현했다.

- **브랜드 소개 페이지**(`/brand-story`): 헬스보이짐 브랜드 스토리를 전달하는 온라인 얼굴.
- **검색엔진 최적화(SEO)**:
  - Next.js Metadata API로 **페이지별 title·description·OpenGraph**를 개별 관리(11개 페이지), 사이트 전역 title 템플릿·`metadataBase` 설정.
  - **동적 사이트맵**(`sitemap.ts`): 18개 URL을 priority·changeFrequency와 함께 자동 생성.
  - **구글·네이버 서치콘솔 사이트 인증** 토큰 등록으로 색인 관리.
  - SSR(App Hosting)로 검색 크롤러에 완성된 HTML 제공.
- **전환 측정 파이프라인**: Google Tag Manager, **Meta(Facebook) Pixel**, **네이버 애널리틱스**(wcslog), **당근 픽셀**을 심어 광고·유입 성과를 추적할 수 있는 마케팅 계측 기반 구축.

> 결과: 별도 광고 없이도 브랜드/상품 키워드로 **네이버·구글 검색 상단에 노출**되어, 프랜차이즈의 온라인 유입 창구로 작동.

## 8. 기술적으로 신경 쓴 부분

- **보안 규칙 설계**: Firestore 규칙에서 이메일 기반 `isAdmin()` 게이트로 공개-읽기/관리자-쓰기 분리. 상담·등록 문서는 누구나 생성 가능하되 읽기·수정은 인증자만, 클라이언트 삭제는 원천 차단.
- **CSV Injection 방어**: 관리자 신청자 목록 CSV 내보내기에서 `= + - @` 등으로 시작하는 셀을 무력화해 스프레드시트 수식 실행 공격 차단.
- **시크릿 분리**: 지오코딩 시크릿은 서버 런타임(App Hosting Secret)에만 두고 클라이언트 번들에 노출하지 않도록 `apphosting.yaml`의 `availability`를 BUILD/RUNTIME으로 구분 관리.
- **점진적 데이터 마이그레이션**: 정적 JSON → Firestore로 전환하면서, 데이터 계층마다 폴백을 두어 **무중단으로 단계 전환**. 구 팝업 스키마는 자동 마이그레이션 처리.
- **운영 제약 대응 배포**: 저장소 히스토리가 대용량 미디어로 약 2GB까지 커져 일반 push가 실패하는 문제를, **현재 코드만 담은 orphan 커밋 스냅샷 배포**로 우회.

## 9. 성과 · 배운 점

- **공식 웹사이트 부재 → 검색 상단 노출**: 온라인 브랜딩이 불가능하던 프랜차이즈에 검색으로 발견되는 대표 웹을 만들어 냄.
- **기획→개발→배포→운영 전 과정을 혼자** 책임지며 실제 사업 서비스를 런칭·유지.
- "코드를 건드리지 않고도 운영이 굴러가는" 구조를 목표로, **콘텐츠와 코드를 분리한 CMS 아키텍처**를 설계·구현.
- 알고리즘(등급 추천), 외부 API 연동(지도·지오코딩), 실시간 DB, 보안 규칙, SEO, SSR 배포까지 **풀스택 범위를 실전에서 경험**.
